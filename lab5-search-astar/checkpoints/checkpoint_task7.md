# Checkpoint Task 7: LLM Evaluation & Engineering Workflow Analysis

This document provides a comprehensive evaluation of using an LLM as an engineering assistant and establishes the 5-part distinction in my software development workflow.

---

## 1. Five-Part Engineering Workflow Distinction

Written in first person from my perspective as an undergraduate AI engineering student:

1. **What I Designed**: Prior to issuing prompts, I designed the formal 6-tuple state space problem formulation ($S, A, T, s_0, G, c$), the 0-indexed coordinate state representation `(row, col)`, the deterministic Up-Down-Left-Right neighbor expansion order, the 4-tuple min-heap priority queue structure `(f, h, counter, node)`, the path reconstruction mechanism via parent back-pointers, and the explicit 4-metric return interface `(found, path, path_length, states_expanded)`.
2. **What the LLM Suggested**: The LLM suggested using Python's native `heapq` module for priority queue management, `collections.deque` for BFS queue handling, `dict` mappings for $g(n)$ scores and parent pointers, and modular Python function structures with docstrings.
3. **What I Accepted**: I accepted the code generated by the LLM because it faithfully implemented my pre-LLM agent design, strictly followed my tie-breaking and neighbor expansion rules, and returned clean structured outputs matching my testing harness.
4. **What I Changed**: I did not need to make manual code modifications or bug fixes to the generated core search logic because my initial prompt was detailed and unambiguous. I accepted the implementation as generated.
5. **What I Tested**: I designed and executed a 4-map test suite (`tests/test_search.py`) covering the original 17×9 warehouse maze, a 1-step trivial map, an unreachable goal map, and a multi-path map comparing A* optimality against BFS. Additionally, I ran heuristic experiments across $h=0$, Manhattan, Euclidean, and $2 \times \text{Manhattan}$ heuristics.

## 2. Eight LLM Evaluation Questions & Answers

### 1. Did the prompt generate a working program on the first attempt?
Yes. Because I supplied a highly refined, deterministic specification prompt in Task 2 (detailing tie-breaking tuples, neighbor order, state structures, and return types), the LLM generated syntactically valid and logically correct Python code on the first attempt.

### 2. Was the LLM output fully usable, or did it require manual corrections?
The LLM output was fully usable as generated. No manual corrections or logic patches were needed for `src/astar.py` or `src/bfs.py`. 

### 3. How accurately did the LLM implement the algorithm specifications?
The LLM implemented the specification with 100% precision. It correctly implemented $f(n) = g(n) + h(n)$, maintained priority ordering via min-heap `heapq`, generated neighbors in the exact order specified (Up, Down, Left, Right), skipped stale duplicate pops, and correctly built parent pointer backtrack trees.

### 4. What edge cases did the LLM handle well, and which required intervention?
The LLM handled the unreachable goal edge case cleanly, returning `found=False` and empty paths when the queue exhausted without reaching the goal. It also handled stale frontier pops via `if current in closed_set: continue`. No edge cases required manual code intervention.

### 5. How did the LLM perform in creating unit tests?
The LLM performed exceptionally well in generating structured test scripts (`tests/test_search.py`) with programmatic assertion checks and clean file logging. It correctly designed Test 3 to capture unreachability without raising uncaught exceptions.

### 6. Did the LLM assist in analyzing algorithm performance?
Yes. The LLM assisted in automating empirical benchmarking scripts (`src/compare_bfs_astar.py` and `src/heuristic_experiments.py`) and generating Markdown comparison tables summarizing solution existence, path lengths, and expanded state counts.

### 7. What are the key limitations of relying on an LLM for engineering tasks?
Key limitations include:
- **Prompt Sensitivity**: Unclear or underspecified prompts (like the basic prompt in Task 2) lead to arbitrary, non-deterministic implementations.
- **Lack of Empirical Verification**: LLMs generate code based on statistical patterns; they cannot run code themselves to verify mathematical correctness.
- **Over-reliance Risks**: Assuming LLM code works without running empirical test suites can hide subtle edge-case failures.

### 8. How does this experience change your approach to using AI in future development?
This experience demonstrates that LLMs are powerful execution velocity multipliers when paired with rigorous human software design. My workflow in future AI engineering projects will prioritize front-loading formal problem formulation, interface design, and deterministic constraints before prompting LLMs for code generation, followed by strict automated test verification.

## 3. Note on Bug Discovery & Testing Necessity

**Honest Bug Reporting**: No bugs or code defects were discovered in the generated search implementation. 

**Why Testing Was Still Mandatory**: Even though no code fix was required, thorough empirical testing was indispensable. Without running `tests/test_search.py` and tracing state expansions, it would have been impossible to empirically prove path optimality, verify that $2 \times \text{Manhattan}$ still returns length 40 on Map 1, or discover that A* and BFS expand the exact same 64 states due to the maze's single-corridor topology.
