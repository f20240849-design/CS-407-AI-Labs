### Question 1: What is the difference between a Prolog fact and a Prolog rule?

**Answer:**  
- **Prolog Fact:** An unconditional assertion that a property or relationship holds true in the world. It consists of a single predicate clause ending with a period (e.g., `connected(a, b).`). Facts form the ground truth of the knowledge base.
- **Prolog Rule:** A conditional implication stating that a head predicate is true *if* one or more body predicates are true. It uses the `:-` operator (read as "if"), separating the head from the body (e.g., `can_move(X, Y) :- connected(X, Y).`).

### Question 2: How does a Prolog query correspond to asking whether something follows from a knowledge base?

**Answer:**  
Submitting a query `?- Goal.` to Prolog is formally equivalent to asking whether the knowledge base $KB$ logically entails the proposition ($\text{KB} \models \text{Goal}$). 

Prolog uses **SLD resolution** (backward chaining) to search for a deductive proof. If Prolog can construct a proof chain from the facts and rules in $KB$, it returns `true.` (along with any variable unifications). If no proof can be constructed under the Closed-World Assumption, it returns `false.`.

### Question 3: Why might it be useful to use a Prolog program to verify a plan generated by a Python program?

**Answer:**  
Python planning scripts rely on imperative control loops (`while`, `for`, list indexing) that can easily suffer from subtle software bugs, state mutation leaks, or incomplete precondition evaluation. 

Using Prolog as an independent verifier separates **domain logic** from **search execution**. Prolog rules state *what* constitutes a valid transition in pure logic, providing a clean, declarative benchmark to check whether the Python program's output violates any fundamental rules.

---

### Question 4: What advantage does an independent verifier provide when the original plan was generated with the help of an LLM?

**Answer:**  
Large Language Models (LLMs) operate probabilistically via token prediction and lack formal reasoning bounds. Consequently, an LLM can generate a candidate plan that *looks* plausible in text but contains illegal actions or hallucinations (e.g., moving between unconnected locations or dropping items not held).

An independent verifier (such as a Prolog engine or Python state simulator) acts as an automated, non-probabilistic safety gate. It enforces zero-tolerance verification: candidate plans must strictly pass deterministic logical rules before being approved for execution on real physical hardware.
